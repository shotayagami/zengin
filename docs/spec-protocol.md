# 実装仕様 (学習用・Tailscale網内)

全銀協標準通信プロトコルを、このプロジェクトでどこまで、どう実装するかを定める文書。
仕様が曖昧な箇所の判断も、ここに書く(§5)。調査内容は `protocol-notes.md` を参照。

下の `§n` は全銀協の仕様書「全銀協標準通信プロトコル -TCP/IP手順・広域IP網-」の章番号、`別冊` は「適用業務およびレコード・フォーマット」別冊の章番号。
どちらも全銀協のサイトで公開されている(`scripts/fetch-refs.sh` で `ref/` に取得できる。著作権は全銀協にあり、このリポジトリには含めない)。
この文書は、規約(プロトコルの取り決め)を自分の言葉で書き直したもので、仕様書の代わりにはならない。

## 1. スコープ

この文書は、全銀協標準通信プロトコルの実装の範囲を定める。
その上に載せる、中央の全銀ネットと銀行ノードは `spec-net.md`。そこでは §2 の `serve`/`send`/`fetch` は、
セッション層に差し込むファイルの受け渡しインタフェース(`handler.rs`)の実装として作り直す。

| 項目 | 決定 |
|---|---|
| 言語 | Rust。依存クレートは使わず std のみ(テストを書く場合も std のみ) |
| 通信 | 同期 I/O (`std::net`)。接続ごとにスレッドを1つ立てる |
| 役割 | 一次局(TCP要求側)と二次局(TCP受諾側)の両方を実装する |
| 接続相手 | Tailscale 網内のみ。実在の銀行とは接続しない |
| ポート | 既定は TCP 5020 (§III)。`--listen` で変更可 |
| 暗号化 | 実装しない。Tailscale(WireGuard)に任せる(§IV が方式を規定していないため仕様上問題ない) |
| 業務 | 総合振込(21, 連絡, 120B)、給与振込(11, 連絡, 120B)、振込入金通知(01, 照会, 200B, フォーマットA) |
| 文字コード | JIS と EBCDIC の両方 (ヘッダのコード区分 0/1) |
| 圧縮 | 実装する (§X)。ファイル単位で切り替え |
| 論理ACK連続送信 | 実装する (§VIII)。MN は 0〜15 で設定可能 |
| 接続あたりのファイル数 | いくつでも (マルチファイル伝送)。連絡と照会が混ざるときは、ファイルの間でモード変更をする |
| 再送要求 | 同一接続内の再送を実装する。本実装が求めるのは全ファイルの再送 (From=1, To=0xFFFF)。受けた再送要求は、テキスト番号の範囲指定にも応じる。接続をまたぐ回復は、照会モードだけ実装する (開始要求の代わりの再送要求。一次局は `fetch --resend`) |
| 対象外 | 暗号化接続、IPv6 固有の考慮、PSTN版、ファイル名補助情報の中身、上記以外の業務、Shift_JIS、拡張Z手順(テキスト長の拡張)、二重ファイル伝送チェック |

## 2. 構成

```
src/
  lib.rs        モジュール宣言
  charcode.rs   JIS/EBCDIC 変換 (charcodes.txt の表を読む)
  sublayer.rs   SH(8B)、論理ACK、MN/AF の管理
  text.rs       TTC(5B)、テキストの組み立て、圧縮/復元
  control.rs    制御電文 64B (通信制御、ファイル制御) のエンコード/デコード
  record.rs     固定長レコードとファイルの組み立て・検証 (総合振込、給与振込、振込入金通知、為替通知)
  session.rs    電文制御 (一次局 send_file/fetch_file、二次局 serve)
  handler.rs    二次局が呼ぶ、ファイルの受け渡しインタフェースと、相手ごとの認証情報
  server.rs     二次局の待ち受けと定期処理のスレッド
  exchange.rs / net.rs / bank.rs / store.rs   全銀ネットと銀行ノード (spec-net.md)
  config.rs     設定ファイル (key = value、[種類 名前] のセクション)
  main.rs       CLI
tests/          ループバックの結合テスト、堅牢性、状態の復元、バイナリの結合テスト
```

CLI の使い方は `spec-net.md` §7 と `README.md`。二次局は `handler.rs` の `Handler` を実装して差し込む。
接続先ごとの設定(センター確認コード、パスワード、ファイルアクセスキー)は `PeerCfg` で、設定ファイルから作る。

## 3. バイトレイアウト (確定分)

バイナリ整数はすべてビッグエンディアンとする(§に明記なし。判断 D1。日立の製品のトレースで確認)。

### 3.1 サブレイヤヘッダ SH (§V, §VIII) 8バイト

| byte | 内容 |
|---|---|
| 0-1 | メッセージ長 (SH込み) |
| 2 | 上位4bit=版番号(0001) / 下位4bit=識別子(0000=情報、0001=論理ACK) |
| 3 | 上位4bit=AF(0=ACK要求、1=不要) / 下位4bit=MN(連続受信回数) |
| 4-7 | 0x00 |

- 情報メッセージの長さは8以上、論理ACKの長さは8ちょうど。
- 版番号が 0 または識別子が 0/1 以外のメッセージは誤りとして扱い、TCP を切断する。
- 受信側は予備(byte4-7)を検査しない。
- 受信側は MN を開局要求と、その論理ACKからだけ読み取る。以降のメッセージでは無視する。

### 3.2 TTC (§VII) 5バイト

| byte | 内容 |
|---|---|
| 0 | 情報区分。上位ニブル=接続形態(1=PC)、下位ニブル=電文区分(0=制御、1=データ) |
| 1-2 | テキストシーケンス番号 (制御=0、データ=1〜65535) |
| 3-4 | テキスト長 (TTC込み。圧縮時は圧縮後の長さ) |

- 接続形態区分は常に 1 (汎用機-PC) にする。
- テキストは最大2048バイト。120Bレコードなら17件、200Bレコードなら10件まで入る。
- シーケンス番号が1から連続していない場合は TCP を切断する。

### 3.3 通信制御電文 64B (§VII)

| byte | 内容 | 型 |
|---|---|---|
| 0 | 電文区分: 00開局要求 01開局回答 02閉局要求 03閉局回答 04モード変更要求 05モード変更回答 | X(1) |
| 1 | 処理結果 (要求では 0x00) | X(1) |
| 2-8 | 相手センター確認コード = センターコード(10桁BCD, 5B) + CPU/端末コード(4桁BCD, 2B) | X(7) |
| 9-15 | 当方センター確認コード (同上) | X(7) |
| 16-21 | 通信年月日時分秒 (BCD、西暦下2桁) | X(6) |
| 22-27 | パスワード | 6B |
| 28 | アプリケーションID = '0' | C(1) |
| 29 | モード '0'=連絡 / '1'=照会 | C(1) |
| 30-63 | 0x00 | X(34) |

- 日時は BCD で、2026-11-21 10:30:15 なら `26 11 21 10 30 15`。
- C(n) は EBCDIC で、'0' は 0xF0、'1' は 0xF1。
- モード変更要求/回答 (04/05): 一次局が、ファイルとファイルの間で送る (仕様書59〜62頁)。モード変更要求の項目は開局要求と同じで、モードに切り替え後の値を入れる。専用のパスワードはないので、開局要求・開局回答のパスワードを使う。
  二次局は、センター確認コード (11/12)、パスワード (14)、アプリケーションID (15)、モード (16) を検査し、正常ならモード変更回答 (00) を返してモードを切り替える。回答は、ほかの回答と同じく、センター確認コードを入れ替え、残りの項目 (日時を含む) は要求の値にする。
- センター確認コードの検査 (開局要求・閉局要求): 要求の相手センター確認コード (受信側=二次局) が自局でなければ 11、当方センター確認コード (送信側) が登録にない、または開局時の相手と違えば 12。どちらも合っていてパスワードが違えば 14 (仕様書80頁の処理結果コードの表)。
- 仕様書83頁の表の読み方(凡例は無いが、全行で次の読み方と矛盾しない):
  - ○ はコンピュータセンター(二次局)がセットする項目、△ はセンターがチェックする項目(=一次局がセットする項目)を表す(判断 D10)。
    つまり、○ の行は二次局が送る電文、△ の行は一次局が送る電文で、受け取った側は印のある項目をすべて検査する。
  - `-` は使用しない項目で、0x00 を入れて送り、受信側は検査しない。
  - 開局回答/閉局回答は、要求と同じ項目をすべて設定する(センター確認コードは入れ替える。判断 D4)。
    通信年月日時分秒も、自局の時計ではなく要求の値を返す。日立の一次局は、回答の日時・アプリケーションID・モードが要求と違うとエラー(T5/T7/T8)にするため、本実装の一次局も同じ検査をする。
  - パスワードは電文区分ごとに別の値を設定できる。設定ファイルでは4種(開局要求/開局回答/閉局要求/閉局回答)を指定でき、省略時は共通の1つを使う。

### 3.4 ファイル制御電文 64B (§VII)

| byte | 内容 | 型 |
|---|---|---|
| 0 | 電文区分: 10開始要求 11開始回答 12終了要求 13終了回答 14再送要求 | X(1) |
| 1 | 処理結果 (要求では 0x00) | X(1) |
| 2-13 | ファイル名 (EBCDIC) | 12B |
| 14-19 | ファイルアクセスキー | 6B |
| 20-21 | テキスト数 | B(2) |
| 22-24 | レコード数 | B(3) |
| 25 | レコードID '0'=固定長 | C(1) |
| 26-27 | レコード長 (120 または 200) | B(2) |
| 28-31 | 再送指定区分 From(2) To(2) | B(4) |
| 32 | データ圧縮ID '0'/'1' | C(1) |
| 33-49 | ファイル名補助情報。本実装は中身を解釈しない。自分から送る要求では 0x00、回答 (開始回答・終了回答・再送要求) では要求の値をそのまま返す | 17B |
| 50-63 | 0x00 | X(14) |

- ファイル名は `5020` + データコード(4) + サイクル(2) + `0`(補助情報ID) + `0`(ダミー)。
  データコードは 総合振込 `0121`、給与振込 `0111`、振込入金通知 `0001`。サイクルは `01`〜`99`。
- 処理結果コード: 00正常 10電文区分 11ファイル名 12アクセスキー 13テキスト数 14レコード数 15レコード長 16二重伝送 17ファイルなし 18レコードID 19圧縮ID 99その他。
- 項目の使い方 (仕様書83頁の表から。`-` 以外を設定する):
  - 開始要求: ファイル名、アクセスキー、レコードID、レコード長、圧縮ID。
  - 開始回答: 処理結果を加えた同じ項目 (照会モードでは、送るファイルの情報を返す)。
  - 終了要求: 開始要求の項目に、テキスト数とレコード数を加える。
  - 終了回答: 処理結果を加えた同じ項目 (テキスト数とレコード数は、受信して数えた値を入れる)。
  - 再送要求: 開始要求の項目に、再送指定区分を加える。テキスト数とレコード数は使わない。
  - 再送指定区分は再送要求だけで使い、ほかの電文では 0x00 にする。
  - アクセスキーも電文区分ごとに別の値を設定できる。設定ファイルでは共通の1つだけ指定する。
- 通信制御電文の処理結果コード: 00正常 10電文区分 11相手センター 12当方センター 13サービス時間帯 14パスワード 15アプリID 16モード 17モード変更不可 99その他。

### 3.5 データ電文 (§VII, 別冊)

- テキスト = TTC + レコード×n。ファイル全体を、ヘッダ → データ → トレーラ → エンドの順に、テキスト単位で詰めて送る。
- テキストの境界はレコード境界に合わせる。レコードをまたいで分割しない。
- 圧縮(ファイル制御電文の圧縮ID='1')のときは、テキストごとに次の形にする。
  `TTC | 圧縮前テキスト長(2B) | 圧縮データ | 0x00`。圧縮前テキスト長は、TTC の 5 バイトを含む (レコード 240 バイトなら 245。Biware との接続で確認)。
  - 圧縮対象は TTC の後ろのレコード部分だけ。TTC のテキスト長は圧縮後の長さにする。
  - 圧縮制御文字(1バイト)は、上位2bitが種別、下位6bitが個数(1〜63)。
    `00`+個数=後続の個数バイトは無圧縮 / `01`+個数=ゼロ(0xF0)の繰り返し / `10`+個数=スペース(0x40)の繰り返し / `11`+個数=次の1バイトの繰り返し。0x00=圧縮終了。
  - 01と10は EBCDIC 前提(0xF0、0x40)。JIS のデータは 00 と 11 だけで表現する(判断 D5)。

### 3.6 レコード (別冊)

| 業務 | レコード長 | ヘッダ種別コード | コード区分 |
|---|---|---|---|
| 総合振込 | 120 | 21 | 0=JIS / 1=EBCDIC |
| 給与振込(民間) | 120 | 11 | 同上 |
| 振込入金通知 | 200 | 01 | 同上 |

項目の定義は `protocol-notes.md` §6 を正とする。送受信時に次を検証する。

- 各レコードの長さが規定通りで、データ区分が 1→2…→8→9 の順であること。
- トレーラの合計件数と合計金額が、データレコードの実際の件数と合計に一致すること。
- N 項目は数字だけ、C 項目は使用文字表(`src/charcodes.txt`)の文字だけであること。
- 人名欄は別冊付録1の注1(小文字カナ不可、記号は `( ) - .` のみ)に従う。

## 4. 電文制御 (§VI)

仕様書の状態遷移表(40〜43頁)とシーケンス図(44〜62頁)を整理したもの。1つの接続で、開始要求〜終了回答 (または開始回答 NG) を何回でも繰り返せる。
以下では TCP 要求側を「一次局」、受諾側を「二次局」と呼ぶ。

### 4.1 通常の流れ

```
連絡モード                                     照会モード
一次局                  二次局                  一次局                  二次局
connect ───────────────▶                     connect ───────────────▶
開局要求 ──────────────▶                     開局要求 ──────────────▶
        ◀────────────── 開局回答                     ◀────────────── 開局回答
開始要求 ──────────────▶                     開始要求 ──────────────▶
        ◀────────────── 開始回答                     ◀────────────── 開始回答
データ電文×n ──────────▶                             ◀────────────── データ電文×n
終了要求 ──────────────▶                             ◀────────────── 終了要求
        ◀────────────── 終了回答             終了回答 ──────────────▶
閉局要求 ──────────────▶                     閉局要求 ──────────────▶
        ◀────────────── 閉局回答                     ◀────────────── 閉局回答
close (一次局から)                           close (一次局から)
```

各電文は 1 情報メッセージで、論理ACKで確認する(§4.4)。

### 4.2 二次局の状態遷移 (仕様書の S1〜S9)

| 状態 | 受信 | 動作 |
|---|---|---|
| S1 初期 | 開局要求 | 検査して開局回答(OK)を返し S2 へ。項目エラーなら開局回答(NG)を返して切断。それ以外の電文は切断 |
| S2 | 開始要求(連絡) | 検査して開始回答(OK)を返し S9 へ。項目エラーなら開始回答(NG)を返して切断。`resume` が有効で、同じ相手から同じファイルを途中まで受けていれば、開始回答の代わりに続きからの再送要求 (From=最初の抜けの番号、To=全ビットオン) を返して S9 へ |
| S2 | 開始要求または再送要求(照会) | 送るファイルがあれば開始回答(OK)、データ電文、終了要求を続けて送り S6 へ。なければ開始回答(NG,17)を返して S5 へ |
| S2 | 閉局要求 | 閉局回答を返して終了 (ファイルなしの照会は S5 から同じ) |
| S9 データ電文待ち | データ電文 | 検査して保存し S9 のまま |
| S9 | 終了要求 | 件数が一致すれば終了回答(OK)を返し S8 へ。不一致なら終了回答(NG,13/14)を返して切断。データ電文なし (テキスト数 0) の終了要求は、0 バイトのファイルとして終了回答(OK)を返し、検査も確定もしない |
| S9 | (テキスト番号の飛び) | 受けたテキストを捨て、全ファイルの再送要求を返して S7 へ |
| S7 | データ電文 | 保存して S9 へ |
| S8 | 開始要求 | 次のファイル (マルチファイル伝送)。S2 の開始要求と同じ |
| S2 / S4 / S5 / S8 | モード変更要求 | 検査してモード変更回答を返し、モードを切り替えて同じ状態へ。NG なら切断 |
| S4 / S5 / S8 | 開始要求、再送要求(照会) | 次のファイル。S2 と同じ。照会で、同じ接続のなかで同じ種類 (産業別コード+データコード) のファイルをもう一度求められたら、ファイルなし(17) を返す (確定前の同じ内容を2度渡さないため) |
| S8 | 閉局要求 | この接続で受信したファイルをすべて確定してから、閉局回答を返して通信終了 (§4.4) |
| S6 | 終了回答(OK) | S4 へ (閉局要求待ち) |
| S6 | 再送要求 | 範囲のデータ電文と終了要求を再送して S6 のまま。項目エラーなら切断 |
| S4 | 閉局要求 | 閉局回答を返して通信終了 |

どの状態でも、規定外の電文を受けた場合、タイムアウト、TCP 切断のいずれかが起きたら切断する(障害)。

### 4.3 一次局の状態遷移 (仕様書の S10〜S16)

| 状態 | 受信 | 動作 |
|---|---|---|
| S10 開局要求送信後 | 開局回答(OK) | 開始要求を送り S13 へ。NG なら切断 |
| S13 開始要求送信後 | 開始回答(OK)、連絡 | データ電文と終了要求を送り S14 へ |
| S13 | 開始回答(OK)、照会 | S16 へ |
| S13 | 開始回答(NG,17)、照会 | 閉局要求を送り S11 へ |
| S13 | 開始回答(NG,17以外) | 切断 |
| S13 / S14 | 再送要求 | 範囲のデータ電文と終了要求を再送して S14 へ (S13 で受けるのは、相手が前回の受信の続きを求めている場合。仕様書 §VII (2)③⑤) |
| S14 終了要求送信後 | 終了回答(OK) | 次のファイルがあれば、必要ならモード変更要求を送り、開始要求を送って S13 へ。なければ閉局要求を送り S11 へ。NG なら切断 |
| モード変更要求送信後 | モード変更回答(OK) | 開始要求を送り S13 へ。NG なら切断 |
| S16 データ電文待ち | データ電文 | 検査して保存し S16 のまま |
| S16 | 終了要求 | 件数が一致すれば終了回答(OK)を返し、次のファイルへ (S14 と同じ)。不一致なら終了回答(NG,13/14)を返して切断 |
| S16 | (テキスト番号の飛び) | 再送要求を返して S15 へ |
| S15 | 再送範囲のデータ電文 | 保存して S16 へ |
| S11 閉局要求送信後 | 閉局回答(OK) | 切断して通信終了。照会で受信したファイルは、ここで確定する。途中で失敗したら、その接続のファイルはどれも確定しない |

### 4.4 共通の規則

- 二次局は、接続後 30 秒以内に開局要求が来なければ切断する。無通信監視タイマも 30 秒で、タイムアウトしたら切断する。
- 仕様書は、閉局要求/回答が正常にやり取りされたあとでファイルを確定するとし(§VI 1(5))、次の場合は破棄するとしている。
  - 終了要求/回答が正常にやり取りされなかった。
  - 閉局要求/回答が正常にやり取りされなかった。
  - データ電文の途中で切断された。
- 本実装は、確定の時点を、受け取る側が連絡モードで受信するときだけ、仕様書より少し早める。
  二次局は、有効な閉局要求を受けたら、**閉局回答を返す前**にファイルを確定する(`Handler::commit_recv`)。
  返してから確定すると、その間に落ちたとき、送信側は成功と思ってファイルを捨て、受信側にも残らず、データが消えるため。
  閉局回答が送信側に届かず再送されうるので、ハンドラは重複を無視しなければならない(少なくとも1回は処理される)。
  照会モードで一次局が受信するファイルは、閉局回答を受け取ってから確定する。照会で二次局が渡したファイルは、閉局回答を返したあとで確定する(受け取れなければ、次回も返す)。
- テキスト番号の飛びは、仕様書の本文(§VII 1(5) 注2)では切断だが、状態遷移表では再送要求になっている。
  本実装は状態遷移表に従い、再送要求を返す。求めるのは全ファイルの再送 (46頁の図(a) の形) で、それまでに受けたテキストは捨てる。
  市販の PC 用クライアント (Biware) は、同一接続内の再送要求に対応しておらず、受けると異常終了する。その場合も本実装は何も確定していないので、相手が接続し直して送り直せば、正常に処理する。
- 接続をまたいだ回復 (仕様書 §VII の本文では、こちらが原則): 照会モードで、一次局が開始要求の代わりに再送要求 (全ファイル) を送ってきたら、二次局は開始回答を返さずに、データ電文と終了要求を送る。送るファイルがなければ、開始回答 (処理結果 17) を返す (この場合の返し方は仕様書にないので、本実装の判断)。
  一次局は、`fetch_file` の `resend` (CLI は `fetch --resend`) で、再送要求から始める。開始回答を待たずにデータ電文を受け、開始回答 (NG) が来たらその処理結果に従う。
  連絡モードで開始要求に再送要求を返すこと (46〜49頁の (b)(d)) は実装しない。途中までの受信を残さないので、開始回答を返すのと同じ結果になる。
  ただし再送要求の受信と、再送の実行はどの状態でも実装する。
- 論理ACKは §VIII の規則に従う。
  - 制御電文を含むメッセージには常にACKを要求する(AF=0)。
  - データ電文は、相手の MN 以下の件数まで AF=1 で連続送信できる。次のメッセージは AF=0。
  - 相手の MN が 0 のときは、すべてのメッセージで AF=0 にする。
  - 自局の連続受信数が自局の MN を超えたら、TCP を切断する。
  - 切断はどちらの側からでも行える。正常終了時は一次局から切断する。

### 4.5 資源の上限

信頼できない相手の入力で、資源を使い果たされないように、次の上限を設ける。

| 項目 | 既定 | 設定 |
|---|---|---|
| 同時接続 (待ち受け側) | 64。超えた接続は、読まずに閉じる | `server.rs` の定数 |
| 受信するファイルの大きさ | 16 MiB。超えたら切断 | `Opts::max_file` |
| 1接続の全体の時間 (待ち受け側) | 300 秒。1バイトずつ遅く送り続ける相手も、この時間で切れる | `Opts::max_session` |
| 無通信監視タイマ | 30 秒 | `Opts::timeout` |
| 再送要求の回数 | 3 回 | `session.rs` の定数 |
| 圧縮の復元後の長さ | 圧縮前の長さの申告まで | `text.rs` |
