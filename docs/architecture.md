# 本来の構成と、このプロジェクトでの簡略化

このプロジェクトの銀行ノードは、学習用に、通信サーバと「銀行の中身」(口座、取引、業務処理) を1つのプロセスにまとめている。
口座は設定ファイルで作り、状態はテキストファイルに保存し、担当者の操作はファイルを介して渡す。

この文書は、実際に銀行がファイル伝送の仕組みを持つときの一般的な構成を示し、このプロジェクトのどこを置き換えれば
その形になるかを書く。銀行ごとに構成は違い、ここに書くのは公開されている情報と製品の資料から整理した例である。
特定の銀行の構成ではない。

## 1. 一般的な構成

```
                    ┌──────────────────────── 銀行 ────────────────────────────────────┐
                    │                                                                  │
 企業 ──インターネット│─▶ ① 対外接続             ② ファイル伝送サーバ                     │
 (全銀TCP/IP、TLS)  │    TLS 終端・FW・接続制限 ─▶ 全銀協プロトコル、ファイル保管、       │
                    │                           受付の記録、照会用ファイルの払い出し     │
                    │                                   │ ▲                              │
                    │                                   ▼ │ (API / キュー / ファイル連携) │
                    │                           ③ 業務システム (EB/FB 業務)              │
                    │                           受付の検査、承認、締め、結果の作成       │
                    │                                   │ ▲                              │
                    │                                   ▼ │                              │
                    │      ⑤ 為替系 / RC ◀──── ④ 勘定系 (口座の原簿、元帳、取引明細)    │
                    │           │                                                      │
                    └───────────┼──────────────────────────────────────────────────────┘
                                ▼
                         全銀システム (全銀センター) ─── 他の銀行
```

| 番号 | 役割 | 主な処理 |
|---|---|---|
| ① 対外接続 | 外から届く通信の入口 | TLS 終端 (証明書)、ファイアウォール、接続元の制限、監視 |
| ② ファイル伝送サーバ | 全銀協プロトコルを話す | 開局・ファイル受信・照会への応答。受け取ったファイルは中身の処理をせず、保管して受付番号を付け、③ へ渡す |
| ③ 業務システム | 業務ごとの処理 | 形式と内容の検査、企業側の承認 (Web 画面などで)、取組日・締め時刻の管理、④ への依頼、処理結果明細・通知ファイルの作成 |
| ④ 勘定系 | 銀行の口座の原簿 | 口座、残高、取引の記帳。入出金は必ずここで行う。トランザクションと監査ログを持つ |
| ⑤ 為替系 / RC | 他行との為替 | 為替通知の作成と送受、全銀システムとの接続 (中継コンピュータ)。日中の仕向超過額や決済の管理 |

ポイント:

- ② は「通信と保管」だけを受け持ち、口座には触らない。受け取ったファイルを確定したら、すぐに受付を返す。
  引き落としなどの重い処理は、③④ が後で (取組日や締め時刻に) 行う。
- ④ が唯一の正しい残高を持つ。②③ は ④ の API を通してしか口座を変えない。
- 照会で渡すファイル (振込入金通知、入出金明細、処理結果明細) は、③ があらかじめ作って ② に置くか、② の求めに応じて ③ が作る。

## 2. このプロジェクトとの対応

| 本来の構成 | このプロジェクト | 主なコード |
|---|---|---|
| ① 対外接続 | Tailscale (WireGuard)、または前に置く TLS 終端 | `docs/tls.md`、`scripts/tls-relay.py` |
| ② ファイル伝送サーバ | 銀行ノードの通信部分 | `src/session.rs` (`serve`)、`src/server.rs`、`Handler` (`src/handler.rs`) |
| ③ 業務システム | 銀行ノードの中で、受信を確定したときにすぐ処理する | `src/bank.rs` (`process_company_file`)、`src/bank/biz.rs` |
| ④ 勘定系 | 銀行ノードの中の口座の表と、テキストの状態ファイル | `BankState::accounts`、`post` (`src/bank/biz.rs`)、`accounts.tsv`、`history.tsv` |
| ⑤ 為替系 / RC | 銀行ノードが全銀ネットへ為替通知を送る部分 | `flush_to_net` (`src/bank.rs`)、為替通知は独自設計 (`docs/spec-net.md` §3) |
| 担当者の操作 (画面・API) | CLI が依頼をファイルに書き、稼働中の銀行ノードが周期ごとに取り込む | `zengin bank recall`、`zengin bank publish` |
| 口座の開設 | 設定ファイルの `[company]`・`[account]` | `BankState::from_conf` |

簡略化しているところ:

| 項目 | このプロジェクト | 本来 |
|---|---|---|
| 処理の時点 | ファイルを受け取ったとき (閉局回答の前) に、すぐ引き落とす | 受付だけ返し、取組日・締め時刻にまとめて処理する。企業側の承認を挟むことが多い |
| 状態の保存 | 処理ごとに、すべての状態を1つのテキストファイルに丸ごと書き直す (1回の置き換えなので原子的。ただし状態が大きいと遅い) | データベースのトランザクション。残高の変更と送信待ちの登録は同じトランザクションで行う |
| 重複の防止 | 受け取ったファイルの指紋 (企業、日付、名前と中身) | 受付番号と、勘定系への依頼ごとの冪等キー |
| 担当者の操作 | 依頼のファイルを周期ごとに取り込む。結果は返らない | 画面や API で、その場で処理して結果を返す。操作の権限と記録を持つ |
| ローン・外為など | 担当者が登録したファイルを渡すだけ | ③④ が、ローンや外為のシステムのデータから作る |
| 口座の照合 | 口座の名義を、スペースと英字の大小を無視して比べる | 名義の正規化 (法人略語、濁点など) の規則と、他行の口座は全銀システムでの照会 |

## 3. 実装例

ここからは、このプロジェクトを本来の構成に近づけるときの設計例である。コードは説明のためのもので、リポジトリには入っていない。

### 3.1 勘定系とのインタフェース

②③ が勘定系を使うためのインタフェースを、まず決める。冪等キーを必須にし、同じ依頼を2度送っても1度しか記帳されないようにする
(閉局回答が届かず企業が再送したとき、ネットワークの再試行のときに、二重の引き落としを防ぐため)。

```rust
/// 勘定系 (④)。実体は別のプロセスで、HTTP や gRPC、メッセージキューの向こうにある想定。
pub trait CoreBanking {
    /// 入出金を記帳する。同じ `idempotency_key` の2回目以降は、記帳せずに1回目の結果を返す。
    fn post(&self, req: &PostingRequest) -> Result<Posting, CoreError>;
    fn balance(&self, acct: &AccountId) -> Result<Balance, CoreError>;
    /// 取引の明細 (入出金取引明細を作るため)。`after` より後の取引。
    fn transactions(&self, acct: &AccountId, after: Option<TxnId>) -> Result<Vec<Txn>, CoreError>;
    /// 口座の有無と名義の照合 (振込口座照会)。
    fn verify(&self, acct: &AccountId, name: &str) -> Result<Verification, CoreError>;
}

pub struct PostingRequest {
    pub idempotency_key: String, // 例: "受付番号/明細の行番号"
    pub debit: AccountId,
    pub credit: AccountId,       // 他行宛なら、為替の仮受口座など
    pub amount: u64,
    pub value_date: Date,        // 取組日
    pub kind: TxnKind,           // 振込、振替、手数料 …
    pub memo: String,
}
```

このプロジェクトでは、`BankState::post` (`src/bank/biz.rs`) が、この `CoreBanking::post` の役を、冪等キーなしで兼ねている。

### 3.2 ファイル伝送サーバ (②) のハンドラ

② は `Handler` を実装し、受け取ったファイルを保管して受付を記録するだけにする。業務の処理は、③ がキューから取り出して行う。

```rust
/// ② の実装例。`storage` はファイルの保管 (オブジェクトストレージや DB)、`queue` は ③ への受け渡し。
struct Gateway<S: FileStorage, Q: JobQueue> {
    storage: S,
    queue: Q,
    peers: PeerDirectory, // 企業ごとのセンター確認コード・パスワード・キー (秘密情報の保管庫から)
}

impl<S: FileStorage, Q: JobQueue> Handler for Gateway<S, Q> {
    fn validate_recv(&mut self, peer: &PeerCfg, f: &InFile) -> Result<(), u8> {
        // 形式の検査だけをする (レコードの並び、トレーラの合計、文字)。残高の確認などはしない
        let fm = record::kind_from_name(&name_kind(&f.name)).ok_or(FILE_NAME_ERR)?;
        fm.parse(&f.data).map(|_| ()).map_err(|_| OTHER_ERR)
    }

    fn commit_recv(&mut self, peer: &PeerCfg, f: InFile) {
        // 閉局回答の前に呼ばれる。保管と受付の登録を1つのトランザクションで行い、③ への受け渡しは outbox 表から別に流す
        // (保管だけされて受付が漏れる、受付だけされてファイルがない、を防ぐ)
        let receipt = self.storage.store_with_receipt(&peer.name, &f); // 同じ指紋のファイルは同じ受付番号を返す
        self.queue.enqueue_from_outbox(receipt);
    }

    fn start_send(&mut self, peer: &PeerCfg, f: &FileCtl) -> Result<Option<OutFile>, u8> {
        // 照会: ③ が作って置いたファイルのうち、まだ渡していないものを返す
        Ok(self.storage.next_outgoing(&peer.name, name_kind(&f.name)))
    }

    fn commit_send(&mut self, peer: &PeerCfg, f: &OutFile) {
        // 閉局回答のあと: 渡したことを記録する。再送要求に備えて、ファイルは消さずに残す
        self.storage.mark_delivered(&peer.name, f);
    }
    // find_peer、start_recv は省略
}
```

このプロジェクトでは、`impl Handler for BankState` (`src/bank.rs`) が、受信の確定のときに ③④ の処理まで一気に行っている。

### 3.3 業務システム (③) の処理の流れ

総合振込の例:

```
1. ② から受付を受け取る (受付番号、企業、ファイル)
2. 内容の検査: 企業コード、依頼人口座、受取人口座の形式、件数・金額の上限、取組日
3. 企業の承認を待つ (Web の画面で、別の担当者が承認する運用が多い)
4. 取組日の締め時刻に、明細ごとに処理する
   - 自行宛: 勘定系で 依頼人口座 → 受取人口座 を記帳 (冪等キー = 受付番号/行番号)
   - 他行宛: 勘定系で 依頼人口座 → 為替の仮受口座 を記帳し、為替系 (⑤) へ為替通知を依頼する
5. 処理できなかった明細 (口座なし、残高不足) を、企業に知らせる (画面、通知ファイル)
```

預金口座振替は、振替日に勘定系で一括して引き落とし、その結果から処理結果明細 (0191) を作って ② に置く。
入出金取引明細・振込入金通知は、勘定系の取引明細から、日次や一定の間隔で作って ② に置く。

このプロジェクトでは 2〜5 をファイルの受信時にすぐ行い、承認と取組日は扱わない (`docs/spec-net.md` §4.2、§4.8)。

### 3.4 担当者の操作

依頼をファイルに書く代わりに、管理用の API (と画面) を ③ に設ける。

```
POST /accounts                      口座の開設
POST /accounts/{id}/postings        入出金 (冪等キー必須)
POST /recalls                       組戻依頼 { 取扱番号 }
POST /companies/{name}/outgoing     照会で渡すファイルの登録 (住宅ローン、借入金など)
GET  /receipts?company=…            受付の一覧と処理状況
```

どれも、操作した担当者と時刻を記録し、権限を確かめる。結果はその場で返す。
このプロジェクトでは、`zengin bank recall`・`zengin bank publish` が依頼のファイル (`recall-requests.tsv`、`publish-requests.tsv`) を書き、
稼働中の銀行ノードが次の周期で取り込む (`BankState::take_requests`)。

### 3.5 保存

| データ | 本来 | このプロジェクト |
|---|---|---|
| 口座・残高・取引 | 勘定系のデータベース | `accounts.tsv`、`history.tsv` |
| 受け取ったファイル | ファイルの保管庫と受付の表 (同じトランザクションで登録) | 保管しない (処理したら指紋だけ `files.tsv` に残す) |
| 照会で渡すファイル | 払い出し待ちの表 | `outbox.tsv`、`notices.tsv` |
| 為替の送信待ち | 為替系の送信待ちの表 (outbox パターン) | `outq.tsv` |
| 重複の判定 | 受付番号、冪等キー | `files.tsv`、`seen.tsv` |
| 操作の記録 | 監査ログ | `journal.tsv` |

## 4. このプロジェクトを使うときの注意

- 銀行ノードは、上の ①〜⑤ を1つのプロセスにまとめた模擬である。実際の銀行のシステムの設計や、資金を扱う用途には使えない。
- 全銀協プロトコルの部分 (`session.rs`、`sublayer.rs`、`text.rs`、`control.rs`、`record.rs`) は、本来の構成の ② にそのまま当たる。
  ② を作る学習には、`Handler` を自分で実装すればよい (3.2 の形)。
- 勘定系や業務システムを作り込むことは、このプロジェクトの対象外とする。
