# 全銀ネット(中央)と銀行ノードの仕様

`spec-protocol.md` は全銀協標準通信プロトコル(1接続1ファイルの伝送)の仕様で、こちらはその上に載せる、中央の全銀ネットと銀行ノードの仕様。
実際の全銀システムの背景は `docs/zengin-system.md` を参照。

**実際の全銀システムの電文仕様は公開されていない**ので、為替通知のレコードと処理手順は、このプロジェクトで独自に設計する(§3)。実システムとは互換性がない。

## 1. 構成

```
企業ノード                仕向銀行ノード              全銀ネット              被仕向銀行ノード            企業ノード
  │ 総合振込(連絡)          │                          │                        │                        │
  ├────────────────────────▶│ 為替通知91(連絡)         │                        │                        │
  │                         ├─────────────────────────▶│ 為替通知91(連絡)       │                        │
  │                         │                          ├────────────────────────▶│ 口座に入金             │
  │                         │                          │                        │ 振込入金通知(照会)      │
  │                         │                          │                        │◀────────────────────────┤
```

| ノード | 役割 | 全銀協プロトコル上の役割 |
|---|---|---|
| 企業 | 総合振込・給与振込を依頼する。振込入金通知を取得する | 一次局 (`zengin send` / `zengin fetch`) |
| 銀行 | 企業の依頼を受けて為替通知を作る。受け取った為替通知を口座に反映する | 企業と全銀ネットに対しては二次局。全銀ネットへ送るときは一次局 |
| 全銀ネット | 為替通知を宛先の銀行へ中継する。仕向超過額を管理する。清算する | 銀行に対しては二次局(銀行からの受信)と一次局(銀行への配信) |

- 銀行と全銀ネットは互いに待ち受ける。全銀ネットは、被仕向銀行へ自分から接続して為替通知を送る(配信)。
- 銀行は、仕向銀行のとき全銀ネットへ接続して為替通知を送り、被仕向銀行のとき全銀ネットからの接続を受ける。
- 通信はすべて 1接続1ファイル の連絡モード(為替通知)、または照会モード(振込入金通知)。
- 為替通知のファイル転送は、実際の MTデータ伝送(複数の為替通知を一括して送る方式)に相当する。1件ずつ即時に届けるテレ為替の方式は再現しない。
- 暗号化は Tailscale に任せる。
- 常駐プロセスは、銀行ノードの `zengin bank` と、全銀ネットの `zengin net` の2種類。

## 2. 処理の流れ

### 2.1 他行宛の振込

1. 企業が総合振込ファイルを仕向銀行へ送る(連絡モード)。
2. 仕向銀行は、ファイルが確定(閉局まで正常)したら、各データレコードを処理する。
   - 被仕向銀行番号が自行なら、全銀ネットを通さず自行内で入金する(§4.2)。
   - 他行宛なら、振込依頼人の口座から引き落とし(残高不足ならその行を不能にして戻す)、為替通知 91 のデータにする。
   - 為替通知は、まとめて全銀ネットへ送る(連絡モード)。
3. 全銀ネットは、ファイルが確定したら、1件ずつ検査する(§5.2)。
   - 受理した分は仕訳に記録し、宛先の銀行ごとの配信キューに入れる。
   - 受理できない分は、仕向銀行へ返却(92)として戻す。
4. 全銀ネットは、配信キューにある為替通知を宛先の銀行へ送る(連絡モード、為替通知 91)。送れなければ後で再試行する。
5. 被仕向銀行は、確定した為替通知を 1件ずつ処理する(§4.3)。
   - 口座があれば入金して、振込入金通知の待ち行列に積む。
   - 口座がなければ、返却(92, 事由 01)を全銀ネットへ送る。
6. 企業が、振込入金通知を被仕向銀行から取得する(照会モード)。

### 2.2 返却と組戻し

- **振込不能の返却**: 被仕向銀行が入金できない(口座なし)、または全銀ネットが受理できない場合に、仕向銀行へ資金を戻す。返却 92 を使う。
- **組戻し**: 仕向銀行が、すでに完了した振込の取消しを依頼する。
  1. 仕向銀行が組戻依頼 93 を全銀ネットへ送る。全銀ネットが被仕向銀行へ中継する。
  2. 被仕向銀行は、受取人口座の残高が足りれば引き落として、返却 92(事由 03)を送る。
  3. 残高が足りない、または該当する入金がない場合は、組戻不能 94 を送る。
- 返却 92 を受け取った仕向銀行は、元の振込依頼人の口座へ入金し直す。

## 3. 為替通知のフォーマット (独自設計)

すべて固定長 **200バイト** のレコードで、全銀協標準通信プロトコルのデータ電文として送る(レコード長 200、`spec-protocol.md` §3.6 と同じ作法)。
ファイルは、ヘッダ → データ → トレーラ → エンドの4種類のレコードで構成する。型は N(数字、右詰め・前ゼロ)と C(文字、左詰め・後ろスペース)。

### 3.1 ファイル名

`9020` + データコード + サイクル(2桁) + `0` + `0`。

- 産業別コードの `9020` は、このプロジェクト独自のコード(実在の産業別コードではない)。
- データコードは `90` + 種別(91〜94)。

| 種別 | データコード | 内容 | 送る向き |
|---|---|---|---|
| 91 | 9091 | 振込為替通知 | 仕向銀行 → 全銀ネット、全銀ネット → 被仕向銀行 |
| 92 | 9092 | 返却 | 被仕向銀行/全銀ネット → 仕向銀行 (全銀ネット経由) |
| 93 | 9093 | 組戻依頼 | 仕向銀行 → 被仕向銀行 (全銀ネット経由) |
| 94 | 9094 | 組戻不能 | 被仕向銀行 → 仕向銀行 (全銀ネット経由) |

サイクルは、同じ送信元・同じ種別のファイルを、1日のうちに送った順に 01〜99 とする。

### 3.2 共通のヘッダ・トレーラ・エンド

| レコード | 項目 (桁) |
|---|---|
| ヘッダ | データ区分N1=1 / 種別コードN2 / コード区分N1 / 送信元番号N4 / 送信先番号N4 / 作成日N8(西暦YYYYMMDD) / 作成時刻N6(HHMMSS) / ダミーC174 |
| トレーラ | データ区分N1=8 / 合計件数N6 / 合計金額N12 (組戻依頼、組戻不能は 0) / ダミーC181 |
| エンド | データ区分N1=9 / ダミーC199 |

- 送信元番号と送信先番号は、銀行番号(4桁)。全銀ネットは `0000`。
- 銀行から全銀ネットへ送るときの送信先は `0000`。全銀ネットから銀行へ配信するときの送信元は `0000`。

## 4. 銀行ノード

### 4.1 設定と状態

設定ファイル(`key=value`)に次を持つ。

- 自行の銀行番号、名称、待ち受けアドレス、全銀ネットのアドレス。
- 全銀ネットのセンター確認コード、パスワード、アクセスキー。
- 取引先企業の一覧: 企業コード(N10)、センター確認コード、パスワード、アクセスキー、口座(支店番号、預金種目、口座番号)。

状態はデータディレクトリにファイルで持つ。

- `accounts.tsv`: 口座(支店、預金種目、口座番号、名義、残高)。
- `outq.tsv`: 全銀ネット宛の送信待ち。
- `notices.tsv`: 企業へまだ通知していない振込入金 (と取消) の通知。
- `sent.tsv`: 他行宛に送った振込と、その状態 (`sent`、`returned`、`recall-requested`、`recall-refused`、`failed`)。
- `credited.tsv`: 他行から受けて入金した振込 (組戻しの判断に使う)。
- `seen.tsv`、`files.tsv`: 重複の判定に使う記録 (§6)。
- `meta.tsv`: 取扱番号の通し番号、通知の識別子、ファイル名のサイクル。
- `journal.tsv`: 追記専用の記録。入出金、為替通知の送受信、返却、重複判定の履歴を残す。

状態ファイルは、処理のたびに一時ファイルへ書き、ディスクへ書き出してから置き換える。
起動時に、状態ファイルがあるのに読めない、解釈できない場合は、**起動を失敗させる**(黙って初期状態に戻すと、残高や重複の記録が消えるため)。

口座は、設定ファイルの `[company]`(取引先企業の口座)と `[account]`(個人などの口座)で作る。残高は初回だけ設定の `balance` を使い、以降は状態ファイルが優先される。残高の確認は `zengin bank statement` で行う。

### 4.2 総合振込・給与振込を受けたとき

ファイルが確定したら、データレコードを順に処理する。

- 取引先企業(センター確認コードから特定)の口座から、振込金額を引き落とす。残高が足りなければ、その行を不能として記録する(引き落としも送金もしない)。
- 被仕向銀行番号が自行なら、被仕向の口座へ直接入金する。口座がなければ、元の口座へ戻す(返却と同じ記録)。
- それ以外は、為替通知 91 のデータレコードにして、全銀ネット宛の送信待ちにする。
- 同じ企業が、同じ日に、同じファイル名・同じ内容のファイルを再送してきたら、無視する(企業が閉局回答を受け取れずに再送した場合に、二重に引き落とさないため)。
  別の依頼として送りたいときは、ファイル名のサイクルを変える。
- 人名欄(ヘッダの企業名と、データの受取人名)の文字は、別冊付録1の注1に従う。使えない文字があれば、ファイル全体を処理結果 99 で拒否する。
- 取組日(MMDD)は検査しない。受け取った時点で当日の取引として扱う(判断 N3)。
- 手数料は引かない(再現しない)。
- 給与振込(種別 11)も、総合振込(種別 21)と同じ処理にする。

送信待ちは、一定時間ごと(既定 5 秒)に、種別ごとに、全銀ネットへ送る(連絡モード)。
1ファイルは 5000 件、合計金額 999,999,999,999 円までで、超える分は複数のファイルに分ける。
送れなかった場合は、送信待ちに残して再試行する。振込 → 返却 → 組戻依頼 → 組戻不能の順に送り、どれかが送れなければ、あとの種別は送らない(組戻依頼が振込より先に届かないようにするため)。
ファイルに入れられない為替通知 (使えない文字など) があれば、その1件を隔離(`quarantine.tsv` に記録)して、残りは送る。隔離した振込は、引き落とした資金を企業の口座に戻す。

### 4.3 為替通知 91 を受けたとき

全銀ネットから配信された為替通知は、ファイルが確定したら、データレコードを順に処理する。

- 仕向銀行番号と取扱番号の組が、すでに処理済みなら無視する(重複の判定。§6)。
- 支店番号、預金種目、口座番号が一致する口座があれば、入金して、振込入金通知の待ち行列に積む。
- なければ、返却 92 (事由 01) を作って全銀ネットへ送る。

### 4.4 返却 92 を受けたとき

次をすべて満たす返却だけを受け付けて、元の振込の依頼人の口座へ、返却金額を入金する。
満たさないものは無視して記録に残し、重複の記録にも加えない(あとの正しい返却を妨げないため)。

- 自行が送った振込 (取扱番号が `sent.tsv` にある) で、被仕向銀行が一致する。
- 返却金額が、元の金額以下。
- 元の振込の状態が `sent` か `recall-requested` (すでに返却された振込には入金しない)。

### 4.5 組戻依頼 93 を受けたとき

取扱番号に対応する入金 (`credited.tsv`) があり、まだ組戻しされておらず、受取人口座の残高が足りれば、口座から引き落として、返却 92 (事由 03) を送る。
企業への通知は、次のようにする。

- 入金をまだ企業へ通知していなければ、その通知を取り下げる。
- すでに通知していれば、取消の通知 (振込入金通知の取消区分 1) を積む。

残高が足りない、または処理済みなら組戻不能 94 (事由 01) を、該当する入金がなければ組戻不能 94 (事由 02) を送る。

組戻不能 94 を受け取った仕向銀行は、その振込が組戻依頼中 (`recall-requested`) で、被仕向銀行が一致するときだけ、状態を `recall-refused` にする。

### 4.6 振込入金通知の取得 (照会モード)

企業が `zengin fetch` で取得する。

- ファイル名は `5020` `0001` サイクル `0` `0`。
- 企業の口座あての未通知の入金があれば、まとめて 1 ファイルにして返す(別冊のフォーマットA、200バイト)。
  1ファイルは 5000 件、合計金額 999,999,999,999 円までで、超える分は次回の取得で返す。
  - ヘッダの口座は、その企業の口座。
  - データは、勘定日、起算日をその日の日付(和暦YYMMDD)、金額、振込依頼人コードと名称、仕向銀行名、EDI情報。
  - 組戻しで取り消された入金は、取消区分 1 のデータで通知する。トレーラの合計件数・合計金額は取消を除き、取消の件数・金額は別の項目に入れる。
- なければ、開始回答でファイルなし(17)を返す。
- 閉局回答が企業に届いたら、渡した通知を通知済みにする。そうでなければ通知済みにしない(次回も返す)。
- 再送要求で始まった照会 (`zengin fetch --resend`、市販クライアントの「再受信モード」) には、次のように返す。
  - 未通知の入金があれば、通常の取得と同じファイルを返す (前回の取得が途中で終わった場合は、これに当たる)。
  - なければ、その企業に最後に渡し終えたファイルを、同じ内容でもう一度返す。通知済みの状態は変わらない。ファイルは企業ごとに1つだけ残す (`lastnotice.tsv`)。
  - 渡し終えたファイルもなければ、ファイルなし(17)。
  通知の消去は、件数ではなく通知の識別子で行う(取得が重なっても、渡していない通知を消さないため)。

### 4.7 組戻依頼を出す

`zengin bank recall --data DIR 取扱番号` で、自行が仕向銀行の振込について、組戻依頼を出す。
CLI は依頼を状態ディレクトリのファイルに書き、稼働中の銀行ノードが次の周期で取り込んで、組戻依頼 93 を作って送る。

## 5. 全銀ネット

### 5.1 設定と状態

設定ファイルに、加盟銀行の一覧を持つ。

- 銀行番号、名称、アドレス、センター確認コード、パスワード、アクセスキー、仕向超過額の限度額(円)。

状態はデータディレクトリに持つ。

- `ledger.tsv`: 仕訳。為替通知の1件ごとに、受付順の連番、日付、取扱番号、種別(91 振込、92 返却)、支払側、受取側、金額、決済区分(`netting` または `rtgs`)、清算済みか、を記録する。
- `outq.tsv`: 配信待ちの為替通知 (銀行ごと)。配信待ちかどうかは、これで分かる。
- `seen.tsv`: 重複の判定に使う記録 (§6)。
- `meta.tsv`: 清算の回数。
- `quarantine.tsv`: 配信できずに隔離した為替通知。

仕向超過額は、仕訳から作る集計値で、起動時に作り直す。振込の仕訳は、(仕向, 被仕向, 取扱番号) で引けるようにしてある。
状態ファイルがあるのに読めない、解釈できない場合は、起動を失敗させる。

### 5.2 為替通知を受けたとき

銀行から為替通知 91 のファイルを受信し、確定したら、データレコードを1件ずつ検査する。上から順に最初に当たった事由で返却する。

1. 送信元の銀行(センター確認コードから特定)と、レコードの仕向銀行番号が一致しない → 返却 12。
2. 被仕向銀行番号が加盟銀行にない → 返却 10。
3. すでに受理した (仕向銀行, 取扱番号) の組 → 無視する(返却もしない)。
4. 金額が 1億円(100,000,000円)以上 → 決済区分 `rtgs`。仕向超過額管理の対象にしない。取引ごとの即時決済として記録する。
5. 金額が 1億円未満 → 決済区分 `netting`。仕向銀行の仕向超過額に金額を足した値が限度額を超えるなら、返却 11。

検査を通ったら、仕訳に記録し、被仕向銀行の配信待ちに入れる。

仕向超過額は、清算前の `netting` の仕訳で、(仕向として送った金額の合計 − 被仕向として受け取った金額の合計) とする。
返却 92 は、元の振込とは逆向き(被仕向 → 仕向)の取引として加える。

返却は、全銀ネットが作る 92 を、仕向銀行の配信待ちに入れる。

### 5.3 配信

- 配信待ちを、一定時間ごと(既定 5 秒)に、銀行ごと・種別ごとにファイルにして、その銀行へ送る(連絡モード)。種別は 91 振込、92 返却、93 組戻依頼、94 組戻不能。
  1ファイルは 5000 件、合計金額 999,999,999,999 円までで、超える分は複数のファイルに分ける。
- 振込 → 返却 → 組戻依頼 → 組戻不能の順に送り、ある種別が送れなかった銀行には、あとの種別を送らない(組戻依頼が振込より先に届かないようにするため)。
- 送れなければ、配信待ちに残し、次回の周期で再試行する。送れたら、配信待ちから外す。
- ファイルに入れられない為替通知は、その1件を配信待ちから外して `quarantine.tsv` に記録し、残りは送る。

### 5.4 返却 92、組戻依頼 93、組戻不能 94 を受けたとき

- 返却 92: 元の振込の記録(仕向銀行 + 取扱番号)があり、返却金額が元の金額以下であることを確認して、仕向銀行の配信待ちに入れる。元の振込と逆向きの取引として、仕向超過額に反映する。確認できなければ捨てて、記録に残す。
- 組戻依頼 93: 元の振込の記録があれば、被仕向銀行の配信待ちに入れる。なければ、組戻不能 94 (事由 02) を仕向銀行へ返す。
- 組戻不能 94: 全銀ネットが中継した組戻依頼 93 に対する返事で、元の振込の記録があるものだけを、仕向銀行の配信待ちに入れる。それ以外は捨てて、記録に残す。
- 組戻依頼 93、組戻不能 94 では、金額は動かない。

重複の記録は、検査を通って受理したときに付ける。検査で落ちた為替通知が、あとの正しい為替通知を妨げないようにするため。

### 5.5 日次清算

`zengin net settle --data DIR` で、清算前の仕訳を集計して、清算一覧を出力する。
CLI は依頼を状態ディレクトリのファイルに書き、稼働中の全銀ネットが次の周期で実行して、結果を `settle-result.txt` に書く(CLI が待って表示する)。
全銀ネットを止めているときは `--offline --conf FILE` で直接実行できる。稼働中に実行してはいけない(メモリ上の状態で上書きされるため)。

- 銀行ごとに、支払合計(仕向として送った `netting` の金額)、受取合計、差引(受取合計 − 支払合計)を出す。差引が負なら、その行は日銀に払う側。
- `rtgs` の取引は、別の一覧に取引ごとに載せる。
- 差引の合計は 0 になる。0 でなければ内部の不整合なので、エラーにする。
- 出力したら、その仕訳を清算済みにする。清算済みの仕訳は、仕向超過額の計算に使わない。
- 本物の日銀の当座預金への振替は再現しない。

`zengin net report` で、清算前の仕向超過額と配信待ちの件数を確認できる。

## 6. 重複と順序の扱い

**受け取ったファイルは、閉局回答を返す前に確定する**(`spec-protocol.md` §4.4)。
閉局回答を返してから確定すると、その間に落ちたとき、送信側は成功と思ってファイルを捨て、受信側にも残らず、資金が両方の帳簿から消えるため。
その代わり、閉局回答が送信側に届かず、送信側が再送することがありうる(少なくとも1回は処理される)。二重に処理しないよう、受信側が重複を無視する。

| 受信するもの | 重複の判定 |
|---|---|
| 全銀ネットが銀行から受ける為替通知 | (仕向銀行, 取扱番号, 種別) |
| 銀行が全銀ネットから受ける為替通知 | 同上 |
| 銀行が企業から受ける振込ファイル | (企業, 日付, ファイル名と内容の指紋) |

- 為替通知は、返却 92、組戻依頼 93、組戻不能 94 も同じ。重複の記録は、検査を通って受理したときに付ける。
- 照会モードで渡す振込入金通知は、逆に、企業が閉局回答を受け取ってから通知済みにする(受け取れなければ、次回も返す)。企業側は、閉局回答を受け取るまで、ファイルを確定しない。
- 処理は、受信したファイルの順に行う。ファイルをまたぐ順序は保証しない。ただし、振込、返却、組戻依頼、組戻不能は、この順に送る(§4.2、§5.3)。

## 7. CLI の全体像

```
zengin gen sogo|kyuyo --out FILE --client-code N --client-name NAME --bank N --item 銀行:支店:種目:口座:受取人名:金額 ...
zengin send  --conf FILE --file FILE [--kind sogo|kyuyo] [--to ADDR] [--cycle N] [--compress] [--mn N]   (企業: 連絡)
zengin fetch --conf FILE --out FILE [--to ADDR] [--cycle N] [--mn N]                                      (企業: 照会)
zengin bank serve     --conf FILE --data DIR [--listen ADDR] [--interval 秒] [--mn N]                    (銀行ノードの常駐)
zengin bank statement --conf FILE --data DIR
zengin bank recall    --data DIR 取扱番号
zengin net serve  --conf FILE --data DIR [--listen ADDR] [--interval 秒] [--mn N]                        (全銀ネットの常駐)
zengin net report --conf FILE --data DIR
zengin net settle --data DIR [--offline --conf FILE]
```

設定ファイルの例は `examples/` にある。

## 8. 構成

```
src/
  exchange.rs   為替通知 (種別91〜94) のレコード
  handler.rs    セッション層から呼ぶ「ファイルの受け取り」「送るファイルの取得」「送信完了」のインタフェース
  bank.rs       銀行ノード (口座、他行宛の振込、入金、返却、組戻し、振込入金通知)
  net.rs        全銀ネット (仕訳、検査、配信、清算)
  server.rs     二次局の待ち受けと定期処理 (同時接続は 64 まで)
  store.rs      状態ファイルの読み書きと記録
```

セッション層(`session.rs`)は、`handler.rs` のインタフェースだけを呼ぶ。
銀行ノードと全銀ネットは、それぞれ実装を差し込む。

## 9. 判断した点

| # | 内容 | 決めたこと | 理由 |
|---|---|---|---|
| N1 | 為替通知の送り方 | ファイル転送(MTデータ伝送相当) | 全銀協プロトコルを再利用するため |
| N2 | 配信の向き | 全銀ネットが銀行へ接続して送る | 利用者の選択 |
| N3 | 取組日 | 検査せず、受信時点を当日とする | 日付をまたぐ処理は学習の主題でない |
| N4 | 返却事由 | 01 / 03 / 10 / 11 / 12 | 最小限の事由に絞った |
| N5 | 名義の不一致 | 検査しない。口座があれば入金する | 実際の銀行も、番号一致で入金して名義は別途確認することが多い(未確認の一般論) |
| N6 | 大口 (1億円以上) | 限度額管理と差額決済の対象外で、取引ごとに記録 | 公開資料の説明どおり |
| N7 | 1企業1口座 | 振込入金通知は、企業の口座ごとのファイル1つ | 別冊のヘッダが口座を1つしか持たない |
| N8 | センター確認コード | 設定ファイルで自由に割り当てる(銀行 `0000` + 銀行番号4桁 + `00`、全銀ネット `0000000000` を推奨) | 実際は電話番号をもとにするが、模擬では不要 |
| N9 | 組戻し | 全額のみ | 一部組戻しは対象外 |
| N10 | 手数料、担保、流動性供給、稼働時間 | 再現しない | `docs/zengin-system.md` §7 |
| N11 | 取扱番号 | 仕向銀行ごとの永続の通し番号 | 日付つきの番号は、年をまたぐと重なって、重複として捨てられるため |
| N12 | 受け取ったファイルの確定 | 閉局回答を返す前 (照会で渡すものは、返した後) | 返したあとに落ちたときに、資金が消えないようにするため。再送による二重処理は重複判定で防ぐ |
| N13 | 状態ファイルが壊れている | 起動を失敗させる | 黙って初期状態に戻すと、残高や重複の記録が消えるため |
| N14 | 組戻しで取り消した入金 | 未通知なら通知を取り下げ、通知済みなら取消区分 1 で通知する | 企業が、取り消された入金を有効と思い続けないため |
| N15 | 企業からのファイルの重複 | (企業, 日付, ファイル名と内容) が同じものは無視する | 企業が閉局回答を受け取れずに再送しても、二重に引き落とさないため |

## 10. テスト

結合テストは、1プロセスの中で、全銀ネット1つと銀行2つ(と企業)を、ローカルの空きポートで起動して行う。

- 正常: 企業A → 銀行1 → 全銀ネット → 銀行2 → 企業B。残高、振込入金通知、清算一覧を確認する。
- 自行内の振込は、全銀ネットを通らない。
- 口座なし → 返却 01、元の口座へ戻る。
- 被仕向銀行が加盟銀行にない → 返却 10。
- 仕向超過額の超過 → 返却 11。清算後は、また通る。
- 1億円以上 → 差額決済に含まれず、即時決済の一覧に載る。
- 組戻し: 承諾(返却 03)、資金なし(組戻不能 94)。
- 被仕向銀行が停止中 → 配信待ちに残り、起動後に届く。
- 企業が同じファイルを再送しても、二重に引き落とされない (サイクルを変えれば別の依頼になる)。
- 閉局要求のあとに、企業が閉局回答を読まずに切っても、ファイルが確定している。
- 返却・組戻不能の検査 (金額、相手の銀行、組戻依頼中か) と、検査で落ちた為替通知が重複の記録を汚さない。
- 組戻しで、未通知の入金は取り下げ、通知済みの入金は取消の通知になる。
- 5000 件を超える振込が、複数のファイルに分かれて全件届く。
- 使えない文字の人名を拒否する。
- 状態ファイルが壊れていると起動に失敗する。再起動しても残高・重複の記録・清算の状態が残る。
- 設定ファイルの数値が範囲外ならエラーになる。
- 差引の合計が 0 になる。
